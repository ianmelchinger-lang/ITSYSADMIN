The List Was Accurate. The Audit Was Still Right.

An internal audit flagged one line: a warehouse clerk, j.kim, can open the finance team's working files on \\hq-win-01\Finance$. You've been handed the flag. Before doing anything else, you pull up the one artifact that should settle it — the share's own permission list.

\\hq-win-01\Finance$ — share permissions query: j.kim
grp-finance-managersFull Control
grp-finance-staffModify
grp-it-adminsFull Control
grp-warehouse-opsModify
No entry matches "j.kim".

Every line on that list is real, and you read all of it. Nothing is hidden from you.

Based on what you just read, can j.kim open the finance team's working files?

The list was accurate the whole time. j.kim's username was never going to appear on it, because not one line on that list grants anything to a person. Every line grants a group.

j.kim belongs to two of the groups sitting on that exact list. grp-warehouse-ops — her role's own group, which carries Modify on Finance$ grp-finance-staff — left over from an eight-month-old cover assignment, which also carries Modify

Neither membership names her. Both reach her. The permission list told you the truth about itself and nothing about who can actually open the share, because that was never a question the list alone could answer.

What this exposes

An identity's effective access is composed — every group it belongs to, intersected with every permission set on every object those groups touch. No single list, however accurate, shows who can reach what. That has to be computed from more than one source before it can be read at all.
