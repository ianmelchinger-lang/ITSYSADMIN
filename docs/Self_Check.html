          Worked example: configuration and access summary

          Scope and starting point

          This summary covers the configuration and access state of the two servers in the estate, cld-lnx-01 and hq-win-01, from the starting state to the state set out in the target specification. I read the before record for all twenty-nine statements and marked each one before planning any change, traced each false statement to its cause, planned one change for each cause, tried each change in the sandbox, and then compared my plan with the after records for all twenty-nine. I planned nothing the specification did not ask for. Where I saw something worth changing outside the specification, I recorded it under Accepted and open items instead.

          Systems

          Host Address Platform Role Records taken as
          cld-lnx-01 192.168.56.20 Red Hat Enterprise Linux 9 Storefront web tier (nginx), finance working files rmensah, with sudo
          hq-win-01 192.168.56.10 Windows Server 2022, standalone server File server: Finance$, Warehouse, Public r.mensah, in PowerShell run as administrator

          Each server reaches the other by name.

          Findings against the specification

          Eleven of the twenty-nine statements were false at the start. They came from eight causes, and four causes broke more than one statement, so I have grouped the findings by cause rather than by statement.

          1. jkim is still in finance-staff on cld-lnx-01 (A1 false, and with it B3). A1-before.txt shows finance-staff:x:1002:dwhitfield,jkim,poyelaran. The specification puts only the two finance accounts there. Because budget.ods is readable by its group, the membership alone lets jkim read the file: in B3-before.txt, sudo -u jkim cat /srv/finance/budget.ods prints the file's line.

          2. /srv/finance is open to everyone (B1 false). B1-before.txt shows drwxrwxrwx. 2 root finance-staff. Any account on the server could enter the folder and create or delete files in it, and with the setgid bit missing, new files would not take the finance group.

          3. nginx would not survive a restart (C2 false). In C2-before.txt, systemctl is-active nginx prints active but systemctl is-enabled nginx prints disabled. The storefront answers now and would stop answering after the next reboot.

          4. The web console is listening on 9090 (C1 and D5 false). C1-before.txt lists *:9090 beside :22 and :80, and D5-before.txt, recorded from hq-win-01, ends TcpTestSucceeded : True. Nothing in the specification uses the web console, which on this server runs from cockpit.socket.

          5. j.kim is still in grp-finance-staff on hq-win-01 (A5 false). A5-before.txt lists d.whitfield, j.kim and p.oyelaran. This is the same lapsed cover assignment as finding 1, recorded on the other platform.

          6. The warehouse group can change the finance folder (B5 false). B5-before.txt lists HQ-WIN-01\grp-warehouse-ops with Modify, Synchronize, not inherited.

          Findings 5 and 6 together explain B9. B9-before.txt sets the Finance folder's permissions beside the two memberships: the folder grants Modify to both grp-finance-staff and grp-warehouse-ops, and j.kim is in both. She reaches the folder by two independent routes, so closing either one alone would leave B9 false. I traced this before planning the changes, so that I would plan both.

          7. The Public share grants Everyone Full Control (B8 false). In B8-before.txt, Get-SmbShareAccess -Name Public returns a single entry, granting Everyone Full. The other two shares follow the house rule of Authenticated Users Change and Administrators Full. Effective access to Public is already governed by its folder permissions, which B7-before.txt shows grant Users Modify, so this is an exposure only if those permissions are ever loosened. I planned the change for consistency and defence in depth, and I do not claim it closes an open door.

          8. svc-backup is an administrator (A9 false). In A9-before.txt, net localgroup Administrators lists svc-backup beside Administrator, a.novak and r.mensah, and net localgroup "Backup Operators" lists no members. A backup account needs to read files it does not own, which is what Backup Operators grants; it does not need to administer the server.

          The other eighteen statements were already true. I read and recorded their before records as well, because a statement I had not checked is one I could not vouch for.

          Changes

          # Change Command Closes
          1 Remove jkim from finance-staff sudo gpasswd -d jkim finance-staff A1, B3
          2 Restore the finance folder's mode and setgid bit sudo chmod 2750 /srv/finance B1
          3 Set nginx to start at boot sudo systemctl enable nginx C2
          4 Stop the web console and keep it from starting sudo systemctl disable --now cockpit.socket C1, D5
          5 Remove j.kim from grp-finance-staff net localgroup grp-finance-staff j.kim /delete A5, B9 with 6
          6 Remove the warehouse group's entry on the finance folder icacls D:\Shares\Finance /remove:g grp-warehouse-ops B5, B9 with 5
          7 Replace Everyone on Public with the house rule Grant-SmbShareAccess -Name Public -AccountName 'Authenticated Users' -AccessRight Change -Force and Grant-SmbShareAccess -Name Public -AccountName Administrators -AccessRight Full -Force, then Revoke-SmbShareAccess -Name Public -AccountName Everyone -Force. In Server Manager, the same change is made in the share's properties, under Permissions. B8
          8 Move svc-backup from Administrators to Backup Operators Add-LocalGroupMember "Backup Operators" svc-backup, then Remove-LocalGroupMember Administrators svc-backup A9

          Changes 7 and 8 add the new grant or membership before removing the old, so the share and the account are never left with neither. In the sandbox I made changes 5 and 6 one at a time and read B9 after each, which confirmed that each route was real: after change 5 alone, j.kim still reached the folder with Modify through grp-warehouse-ops, and only after change 6 did she reach it not at all. The sandbox also showed that change 4 closes C1 and D5 together, because once nothing listens on 9090 there is nothing for the firewall to let through.

          Accepted and open items

          These are things I noticed and did not change, because the specification did not ask for them. Each is routed to the person who owns the decision.

          D5-before.txt shows the firewall on cld-lnx-01 admitting connections to 9090 before the work, and change 4 stopped the listener without touching any firewall rule, so the rule that admits the web console most likely remains. Once nothing answers on 9090, nothing is reachable there, but the rule would let the console through again if anyone started it. The records do not show the firewall's rules, so I have routed it to the operations lead to confirm and remove.

          The finance owner should confirm that no warehouse process needed the Modify grant removed in change 6. The grant was made for speed during onboarding and nothing in the specification relies on it, but the owner knows the workflow and I do not.

          The backup job that svc-backup runs should be watched on its next run after change 8. If it needed more than Backup Operators grants, it will fail, and the owner of the job should know to expect that possibility.

          A group membership change reaches an account the next time it signs in, so an account already signed in keeps its old reach until then. The records do not show who was signed in when the changes were made. Before relying on changes 1 and 5, whoever makes them should confirm that jkim and j.kim are signed out, or have them sign out.
