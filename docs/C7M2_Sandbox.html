Monitoring and automation

Change what you compare with, and change where the job stops

Two panels, each about one switch on the storefront server, cld-lnx-01. The first holds the week of processor readings from the monitoring records. The second holds the nightly archive script on night 3 from the automation records. Each switch changes one thing, and you can flip it as often as you like. Nothing here is scored, and nothing here touches a real server.

Which hours of this week tell the person on call?

This panel shows the week of hourly processor readings for the storefront server cld-lnx-01, from records P1 to P7, as the share of each hour the processor was busy. The host is busy at 02:00 every night, and that is its normal. On Tuesday at 14:00 it is busier than it usually is at that hour. You are told both now, and nothing is hidden. The switch changes only what each reading is compared with: a fixed line at 80%, or this host's own usual reading for the same hour. The fixed line will alert on every ordinary night and stay silent on Tuesday afternoon. The host's own normal will do the reverse.

When the middle step fails, which later steps run, and what does the script report?

This is the log-archive script archive-logs.sh on the storefront server cld-lnx-01, as night 3 in the automation records found it. It has three steps: make today's folder in /data/archive, archive yesterday's log into it, and delete the original. In this run the archive step will fail, because the archive disk fills part-way through. That is given, not hidden. With the switch off, you will see the script delete the original anyway and report success. With the switch on, you will see the run stop at the failed step and report failure. The stop is a safety control doing its job, not an error for you to fix.
