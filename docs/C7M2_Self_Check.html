      Worked example: monitoring and automation evidence

      Scope

      This document covers how the storefront server, cld-lnx-01, is watched and how its one nightly job runs, ahead of the handover. I read one week of the server's processor readings and the storefront log for the same week, stated what normal looks like, found the one window that departs from it and wrote one alert. I then read the nightly archive script, its scheduler entry and three nights of records, and wrote the changes that make the job stop at a failed step, repeat safely and leave a dated record. Every finding cites the record that shows it. I changed nothing the records did not call for, and I list what I noticed beyond that under Accepted and open items.

      The storefront log for the same hour agrees. L2 counts 139 completed checkouts between 13:00 and 14:00 on Tuesday and lists 17 checkouts that timed out, the first at 13:09:41 and the last at 13:52:48. L1, the same hour on Monday, counts 214 completed checkouts and lists none that timed out. L3, Tuesday's busy hour from 01:00 to 02:00, counts 11 completed checkouts and none timed out, which fits a nightly busy hour that customers do not feel. These records say what happened on Tuesday afternoon and not why.

      The threshold comes from the week itself: the 02:00 line never passed 87 percent and no other line passed 24, so a reading 20 points above usual is well clear of anything ordinary. Against the recorded week the rule fires once, for Tuesday's line stamped 14:00:01 at 61 percent against a usual 20. It does not fire on any of the seven nights at 02:00. A fixed line at 80 percent would have done the reverse: seven alerts, every one for an ordinary 02:00, and silence on Tuesday afternoon.

      The nightly job as found

      S1 shows /opt/ops/scripts/archive-logs.sh: one line of three commands separated by semicolons. It makes today's folder in /data/archive, archives yesterday's storefront log into it with tar, and deletes the original with rm -f. It has no stop after a failed step, no record of its own, and both paths are written into the commands. S2 shows cron running it as root at 03:00 every night, with >/dev/null 2>&1, so anything it prints, errors included, goes nowhere.

      Three things follow. The scheduler's record reads the same on all three nights, so it shows only that the job started. The script runs every step whatever the step before reported, so on night 3 it deleted the original after tar had failed. And a second run is unsafe: on night 2 it replaced the good archive with an empty one, because tar -cf recreates the archive before it finds the log is gone, and the script still reported 0, the status of rm -f, its last command.

      Changes to the job

      The new /opt/ops/scripts/archive-logs.sh, with every change marked:

      #!/bin/bash
# Stop at the first failed step (answers night 3)
set -o errexit
set -o nounset
set -o pipefail

# Name each path once
SRC=/var/log/storefront
DEST=/data/archive/$(date +%F)
FILE=storefront-$(date -d yesterday +%Y%m%d).log
RUNLOG=/var/log/archive-logs.log

# Dated line at the start of each run
echo "$(date '+%F %T') archive-logs started: $FILE" >> "$RUNLOG"

# Check before repeating: if yesterday's log is already gone, do nothing (answers night 2)
if [ ! -e "$SRC/$FILE" ]; then
  echo "$(date '+%F %T') archive-logs finished: $FILE not present, nothing to do" >> "$RUNLOG"
  exit 0
fi

mkdir -p "$DEST"
tar -cf "$DEST/storefront-logs.tar" -C "$SRC" "$FILE"
rm "$SRC/$FILE"

# Dated line at the end, reached only if every step succeeded
echo "$(date '+%F %T') archive-logs finished: $FILE archived to $DEST" >> "$RUNLOG"

      The new crontab line, replacing the one in S2, keeps what the job prints in the same record instead of discarding it:

      0 3 * * * /opt/ops/scripts/archive-logs.sh >> /var/log/archive-logs.log 2>&1

      On night 3 the run would stop at the failed tar, the original log would stay on the server, and the record would hold a started line, the error, and no finished line. On a second run like night 2's, the check finds yesterday's log already gone, writes one line and exits, so the 03:00 archive is left alone. The check says the log is not present rather than archived, because a missing log may also mean it was never written. The script now exits non-zero when a step fails, and rm without -f fails if the file is unexpectedly missing. mkdir -p does nothing when the folder exists. /var/log/archive-logs.log is a new file that this change creates.

      How the next run will be confirmed

      Each run will leave two dated lines in /var/log/archive-logs.log: one when it starts and one when it finishes. Every morning by 08:30, the operator on duty, working as rmensah, reads the last lines of that file with sudo tail -n 5 /var/log/archive-logs.log and expects a started line and a finished line dated that morning, shortly after 03:00. A started line with no finished line, an error between them, or no line at all for that morning is a finding. The operator tells anovak, the IT operations lead, the same morning, and frees space or reruns the job that day. The scheduler's record in /var/log/cron is not enough on its own, because N1-cron and N3-cron read the same on a good night and a bad one.

      Accepted and open items

      The archive disk will stop the job again. N3-evening shows it 96 percent full with 427M free before a 431M log, and nothing in the script removes old archives. With the changes, the next night will stop safely and keep the log on the server, but it will keep stopping until there is room. How long archives must be kept is for the storefront application owner, shaddad, to decide; a second alert on free space in /data/archive is for the operations lead to decide.

      Two days of logs are not fully archived. The archive of 11 November's log, in the folder 2026-11-12, is empty after the second run on night 2, as N2-after shows, and night 3 kept only part of 12 November's, as N3-morning shows. Both originals are gone. The storefront application owner should know, in case anyone asks for either day.

      After a stopped run, freeing space and running the new script again the same day finishes the job, because the check finds yesterday's log still there. If the fix waits past the next night, that night archives only its own yesterday, and the older log stays on the server until someone archives it by hand. The operator on duty should know both.

      The cause of Tuesday afternoon's slow hour is not known. The records show when it happened and that checkouts timed out, not why, and that question belongs to whoever troubleshoots the storefront next.
