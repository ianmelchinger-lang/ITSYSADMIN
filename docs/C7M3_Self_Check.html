      Worked example: troubleshooting runbook

      OHP-4 Troubleshooting Runbook

      How to use this runbook

      This runbook holds one entry for each fault diagnosed on the estate, in the order the records give them. Every entry runs in the same order: the report as it arrived, the report restated as one exact check, the tests and what each reached, the last test that passed and the first that failed, the located cause, the one change made, the original check repeated, and what remains. To find an entry, compare the check in front of you with each entry's restated check. To add one, copy the headings, cite every record by its label, and change nothing until the cause is located.

      Entry 1: cld-lnx-01 cannot reach file sharing on hq-win-01 by name

      Report as received. At 09:12 on Monday 16 November, the configuration check for the connection from cld-lnx-01 to hq-win-01 on TCP 445 printed Ncat: TIMEOUT., as FA1 shows. The same check connected at the configuration work, as D1-after shows.

      Report restated as one check. On cld-lnx-01, working as rmensah, nc -zv -w 3 hq-win-01 445 does not connect within three seconds. It connected at the configuration work and fails from at least 09:12 on 16 November.

      Tests. All five were run on cld-lnx-01, as rmensah.

      TestWhat it reachesRecordResult
      1This server's own addressFA2Passes: enp0s8 is up with 192.168.56.20/24
      2hq-win-01 by its addressFA3Passes: 3 of 3 echo replies from 192.168.56.10
      3File sharing on hq-win-01, by addressFA4Passes: Connected to 192.168.56.10:445
      4The name hq-win-01, looked up on this serverFA5Fails: the name gives 192.168.56.11, not 192.168.56.10, the address that answers in tests 2 and 3
      5File sharing by name: the original checkFA1Fails: Ncat: TIMEOUT.

      The usual pattern tests a gateway between the two ends. Both servers sit on one network, 192.168.56.0/24, with no gateway between them, so there is nothing for such a test to cross, and the name lookup takes its place.

      Last test that passed, and first that failed. Test 3 is the last to pass and test 4 the first to fail. Tests 1 to 3 pass, so this server's address, the way to hq-win-01 and file sharing all hold. Tests 4 and 5 fail, and the one link both of them cross that no passing test does is the name.

      Located cause. FA6 shows the line 192.168.56.11 hq-win-01 in cld-lnx-01's /etc/hosts. This server finds hq-win-01 only through that file, so every connection by name goes to 192.168.56.11, where nothing answers.

      The one change made. The file written again with that one line corrected and the other two lines unchanged, as FA7 shows. Because the command replaces the whole file, FA7 also reads it back, and the two unchanged lines match FA6:

      sudo tee /etc/hosts > /dev/null << 'EOF'
127.0.0.1   localhost localhost.localdomain localhost4 localhost4.localdomain4
::1         localhost localhost.localdomain localhost6 localhost6.localdomain6
192.168.56.10 hq-win-01
EOF

      The original check, repeated. In FA8, getent hosts hq-win-01 now gives 192.168.56.10, and nc -zv -w 3 hq-win-01 445 prints Connected to 192.168.56.10:445.

      What remains. The records show that the line was wrong, not how it came to be wrong. The operations lead, anovak, should decide whether to find out who changed /etc/hosts and when. The connections from hq-win-01 to cld-lnx-01 use hq-win-01's own hosts file, which was not checked this morning; the operator on duty should repeat those checks before the handover.

      Entry 2: the nightly archive job on cld-lnx-01 stops

      Report as received. At 08:30 on Monday 16 November, the morning read of the job's own record shows a started line at 03:00:01 for storefront-20261115.log, two tar errors, and no finished line, as FB1 shows.

      Report restated as one check. On cld-lnx-01, working as rmensah, sudo tail -n 5 /var/log/archive-logs.log shows that the 03:00 run of /opt/ops/scripts/archive-logs.sh on 16 November started and did not finish. It is the first run under the job's changes, so no earlier run under them can be compared.

      Tests. All were run on cld-lnx-01, as rmensah. A stopped job is located by checks that each settle one question, rather than by tests that each reach one link further.

      CheckWhat it settlesRecordResult
      1Where the run stoppedFB1At tar: Cannot write: No space left on device, then no finished line
      2Whether the archive disk has roomFB2No: /dev/sdb1 is 100 percent used with 0 free
      3What fills itFB331 dated folders, back to 2026-10-15; this morning's archive is 0 bytes
      4Whether yesterday's log survivedFB4Yes: storefront-20261115.log is still there, 403117286 bytes

      Last test that passed, and first that failed. Check 2, FB2, settles the cause: the disk the archive step writes to has no room.

      Located cause. The archive disk is full, and nothing removes old archives, so it holds every night back to 15 October. The stop worked as intended: tar failed, the run ended before the step that deletes the log, and yesterday's log stayed on the server. FB4 also lists the logs of 13 and 14 November, because the job did not run on those nights while its changes were made.

      Decision this repair depends on. The storefront application owner, shaddad, has decided that archives are kept for 14 days, counting today. On 16 November that keeps every folder dated 3 November or later and allows every folder dated 2 November or earlier to be removed.

      The one change made. The folders past the 14 days, listed first in FB5 (19 folders, 2026-10-15 to 2026-11-02), then removed and listed again in FB6:

      find /data/archive -maxdepth 1 -mtime +13
sudo rm -r /data/archive/2026-10-* /data/archive/2026-11-01 /data/archive/2026-11-02
find /data/archive -maxdepth 1 -mtime +13

      The second find prints nothing, and FB6 shows the disk at 36 percent with 6.5G free. To finish the night's work the same morning, the job was run again by hand, as FB7 shows: sudo /opt/ops/scripts/archive-logs.sh, exit status 0.

      The original check, repeated. In FB8, the last lines of /var/log/archive-logs.log now end with a started line at 08:52:07 and a finished line at 08:52:49: storefront-20261115.log archived to /data/archive/2026-11-16. FB9 shows the disk at 40 percent with 6.1G free, twelve folders from 2026-11-03, a 403128320-byte archive in 2026-11-16, and storefront-20261115.log gone from the server.

      What remains. Nothing in the job removes folders past the 14 days, so at about 400 megabytes a night the 6.1G free fills again in about two weeks. Whether the removal in FB5 and FB6 becomes a step of the job or a scheduled task of its own, and whether to add an alert on free space in /data/archive, is for the operations lead, anovak, to decide.

      The logs of 13 and 14 November are still in /var/log/storefront, as FB9 shows. The job archives only yesterday's log, so it will never reach them. Where and how to archive them is for the operator on duty to settle with anovak; together they will take about 0.9 gigabytes of the free space.

      The empty archive in 2026-11-12 and the partial archive in 2026-11-13 fall outside the 14 days on 26 and 27 November. Once they are removed, nothing at all remains of the storefront logs of 11 and 12 November. shaddad already knows those two days are not fully archived, and should confirm that removing what is left of them is acceptable.
